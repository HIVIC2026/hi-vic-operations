# Server/domain rules (src/lib)

## Architecture rules
- All admin reads/writes use authenticated server functions with explicit errors; non-admin reads stay RLS-scoped. Why: no false-empty records or weak access.
- Stage-entry guards (Owner Authority, PIESA window, approved payment option, evidence, compliance) live only in `stageEntryBlockers`; authority rules live in `authority.server.ts`. Why: rules change centrally.
- One combined installation quote (rectification lines folded in) carries the single Xero invoice and its configured minimum deposit. Why: deposit must precede rectification scheduling.
- PIESA window length lives in `workflow_settings`; deadline/urgency computed by the `job_piesa_deadlines` view. Why: single source for UI and server.
- Payment display state is derived by the `invoice_status` view (customer-safe columns; internal Xero IDs admin-only via server fn); Xero is the system of record. Why: time-based states need no cron.
- Internal pricing (cost/margin/fee) lives only in admin-only `quote_internals`; customer-facing prices in `quote_items` are inc GST. Why: never expose margins.
- Evidence files live in the private `job-files` bucket, accessed only via server-issued signed URLs. Why: no public evidence URLs.
- See `docs/PORTAL.md` for workflow and the security test matrix.
- Write every server function as a literal `createServerFn(...).middleware(...).inputValidator(...).handler(...)` chain; never wrap `createServerFn` in a helper factory. Why: the compiler only turns literal chains into server calls — a factory made handlers run in the browser.
- Never import `@tanstack/react-start/server` in `*.functions.ts` or modules they import; read request data via a `createMiddleware().server()` (see `request-meta.ts`). Why: that import is denied in the browser bundle and crashes every page.
- Job source lives in `jobs.channel` (+ originating installer business/user), made permanent by the `guard_job_source` trigger; installer-sourced jobs get one quote from the assigned installer and stay payment-gated via `commercialBlocker` until `commercial_model = hivic_invoices_owner`. Why: attribution is audit evidence; installer invoicing isn't defined yet.
- ONE full detailed Xero invoice per accepted quote (unique quote_id, reference `Home Insulation Victoria <job>` (locked 2026-10-03; `XERO_REFERENCE_PREFIX`), all quote lines + negative VEEC line, Inclusive GST, Business Unit = Home Insulation Victoria (legacy Projects never used)); configured minimum deposit (10% / 5%, `splitForOption`) via Xero native Request Deposit raised manually (admin records `deposit_request_raised_*`, never unlocks); PIESA and scheduling open only through `evaluatePaymentGate` (`payment-gate.core.ts`, switch `payment_option_gate_enabled`, route-aware, OFF = blocked); install date = same invoice due date (`balance_due_date`, update flagged `xero_update_pending`, sent only if `XERO_DUE_DATE_UPDATES_ENABLED`); pure logic in `invoice.lifecycle.ts`/`xero.core.ts`, mocked tests `bun test ./tests/`. Why: Xero API cannot create native deposit requests; one invoice keeps totals and audit simple.
- Xero business-unit barrier: `jobs.business_unit` (immutable via `guard_job_source` trigger, set explicitly to 'hivic' in `upsertEnquiry`) must equal 'hivic' before every Xero step — `requireHivicInvoice`/`requireHivicJob` in `xero.server.ts` plus `assertHivicPayload`/`assertHivicReference` in `xero.core.ts`; fail closed. Why: the connected DC Construction Solutions Xero org must never be automated for non-Home Insulation Victoria work.
- Base44 enquiry webhook is verified by Ed25519 (public key in `enquiry.core.ts`, header `x-hivic-signature`, optional `x-hivic-key-id: base44-v1`) before parsing; preliminary result (`preliminary_outcome`/`preliminary_reasons`, planned by pure `planBase44Job`) and `life_support_status` are accepted only from source `base44`; new website jobs always land in `new_enquiry` (preliminary screening is information only, never sets stage); repeat syncs never change stage; `source=qa_test` jobs are hidden from the admin pipeline by default. Why: no shared secret to leak; website result is preliminary.
- Mitti bridge: pure label-based prefill/parse in `mitti.core.ts`, the only network boundary in `mitti.server.ts` (`MITTI_API_TOKEN`, read per call). Sync reads only stored audit IDs, checks the template and Portal Job Number (blocks on mismatch), splits electrical fields → `assessments` and measure-up fields → `planMeasurementUpdate`; never status, PIESA records, stages or quotes. Measure-up-only template comes from `workflow_settings.mitti_measureup_template_id` (never invented). Non-standard or unrated work becomes `is_other` rectification items keyed by `external_key` and flagged `needs_office_pricing`; `completeAssessment` blocks until those items are priced. Why: `completeAssessment` stays the only completion gate, and Lovable never makes up a price.
- Site stage = two requirements: ceiling measure-up in `ceiling_measurements` (one `is_current` row drives quoting) and electrical/PIESA in `assessments`; visit scope derived only by `deriveScope` (`scope.core.ts`) via `jobScope`/`getJobScope`; `advanceSiteRequirements` is the only path to assessment_complete. Why: different people may do each part, and quotes must use the accepted measurement.
- Partner enquiries (property manager / installer partner / electrician-REC) live only in admin-only `partner_enquiries`, fed by signed `/api/public/partner-enquiry` (same Ed25519 key, pure `handlePartnerEnquiry` in `partner.core.ts`); never create jobs; Base44 status stored as `source_status`, admin owns `status`/`internal_notes`. Why: partner onboarding is not customer work and must not pollute the Pipeline.
- Activity 48 signing: quote acceptance creates only the commercial `customer_agreements` record and unlocks invoice/deposit; the official `customer_assignments` form is prepared after installation with verified final facts, then signed lead installer → AP → customer. Legacy quote-stage conditional rows remain immutable history and are superseded before correction. `owner_esc_consents` stays separate (post-booking, ≥24h); `installer_declarations` post-install; `ready_for_veec` needs `effective_complete`. Why: the current prescribed assignment form requires actual completion, installation and price/benefit facts before signing.
- Auto-progression uses only `autoAdvanceJob` via guarded transitions. The dashboard defaults to active work; retained views hold ineligible, finalised, cancelled and QA records. Why: a calm queue without losing audit history.
- Gate 1: ONE pure categoriser `evaluateGate1` (`eligibility.core.ts`, ruleset `GATE1_RULESET_VERSION`) using homeowner answers plus office-recorded/onsite facts only: hard-fail -> needs_onsite -> likely; it never raises internal review; life support/roof/area/rollout hold are `jobs.eligibility_flags`; applied only by `autoDecideEligibility` (idempotent by signature, never over admin); progression via `eligibilityConfirmedFor`. Why: simple, explainable results; real verification happens at the Ready Check and office verified eligibility.
- Property Intelligence is retired: the post-intake worker no longer runs remote lookups and `resolveGate1Facts` ignores `property_facts` and Base44 research; historical intelligence tables/code stay read-only for audit. Why: remote research produced wrong results and unnecessary reviews.
- ESC pre-install controls: pure `esc.core.ts` (`readyToInstall`, `bookingLeadBlocker`, `buildEscPayload`, `staleReasons`, `submissionPatch`), persistence `esc.server.ts`; entry to `evidence_outstanding` is blocked unless READY TO INSTALL (Reg 23A consent, ESC notice sent, PIESA copies to owner + installer all ≥24h before start, PIESA window); installation bookings <24h ahead are rejected; `sent` only via adapter (none configured) or audited manual record with reference (DB check constraint). Portal/internal records stay allowed; autoAdvance graph is regression-tested free of delivery, Xero and Mitti calls. Why: QA must never message real customers or trades.

- Job File = read-only aggregation over existing records: pure `jobfile.core.ts` (`buildDocumentIndex` auto-files by source/kind, `visibleTo` role filter, `buildCorrespondence`, `buildTimeline`, `packSelection`/`planPack`/`buildManifest`), loading + ZIP export (fflate, server-side, stored under `<job>/exports/`, signed link only; >150MB → manifest + 7-day signed links) in `jobfile.server.ts`, server fns in `jobfile.functions.ts`. Why: no booking outside the window, no double-booking.

Why: the portal alone decides cleared-to-start.

- Visit changes (cancellations, no-shows, arrivals, evidence rejections) are permanent rows in append-only `visit_events` (drizzle 0099_visit_events); rules in pure `visit-events.core.ts`, persistence in `visit-events.server.ts`. Matching reliability reads real 90-day counts via `reliabilityFor`. Why: one audited source for reliability and no silent rebooking.
