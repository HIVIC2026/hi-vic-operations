## Architecture rules
- All admin reads/writes use authenticated server functions with explicit errors; non-admin reads stay RLS-scoped. Why: no false-empty records or weak access.
- Stage-entry guards (Owner Authority, PIESA window, 50% deposit, evidence, compliance) live only in `stageEntryBlockers`; authority rules live in `authority.server.ts`. Why: rules change centrally.
- One combined installation quote (rectification lines folded in) carries the single Xero invoice and 50% deposit. Why: deposit must precede rectification scheduling.
- PIESA window length lives in `workflow_settings`; deadline/urgency computed by the `job_piesa_deadlines` view. Why: single source for UI and server.
- Payment display state is derived by the `invoice_status` view (customer-safe columns; internal Xero IDs admin-only via server fn); Xero is the system of record. Why: time-based states need no cron.
- Internal pricing (cost/margin/fee) lives only in admin-only `quote_internals`; customer-facing prices in `quote_items` are inc GST. Why: never expose margins.
- Evidence files live in the private `job-files` bucket, accessed only via server-issued signed URLs. Why: no public evidence URLs.
- See `docs/PORTAL.md` for workflow and the security test matrix.
- Write every server function as a literal `createServerFn(...).middleware(...).inputValidator(...).handler(...)` chain; never wrap `createServerFn` in a helper factory. Why: the compiler only turns literal chains into server calls — a factory made handlers run in the browser.
- Never import `@tanstack/react-start/server` in `*.functions.ts` or modules they import; read request data via a `createMiddleware().server()` (see `request-meta.ts`). Why: that import is denied in the browser bundle and crashes every page.
- Job source lives in `jobs.channel` (+ originating installer business/user), made permanent by the `guard_job_source` trigger; installer-sourced jobs get one quote from the assigned installer and stay payment-gated via `commercialBlocker` until `commercial_model = hivic_invoices_owner`. Why: attribution is audit evidence; installer invoicing isn't defined yet.
- ONE full detailed Xero invoice per accepted quote (unique quote_id, reference `HI VIC <job>`, all quote lines + negative VEEC line, Inclusive GST, Business Unit = Home Insulation Victoria (legacy Projects never used)); 50% deposit via Xero native Request Deposit raised manually (admin records `deposit_request_raised_*`, never unlocks); gate opens only when Xero cumulative AmountPaid ≥ 50% or audited override; install date = same invoice due date (`balance_due_date`, update flagged `xero_update_pending`, sent only if `XERO_DUE_DATE_UPDATES_ENABLED`); pure logic in `invoice.lifecycle.ts`/`xero.core.ts`, mocked tests `bun test ./tests/`. Why: Xero API cannot create native deposit requests; one invoice keeps totals and audit simple.
- Xero business-unit barrier: `jobs.business_unit` (immutable via `guard_job_source` trigger, set explicitly to 'hivic' in `upsertEnquiry`) must equal 'hivic' before every Xero step — `requireHivicInvoice`/`requireHivicJob` in `xero.server.ts` plus `assertHivicPayload`/`assertHivicReference` in `xero.core.ts`; fail closed. Why: the connected DC Construction Solutions Xero org must never be automated for non-HI VIC work.
- Base44 enquiry webhook is verified by Ed25519 (public key in `enquiry.core.ts`, header `x-hivic-signature`, optional `x-hivic-key-id: base44-v1`) before parsing; preliminary result (`preliminary_outcome`/`preliminary_reasons`, planned by pure `planBase44Job`) and `life_support_status` are accepted only from source `base44`; new website jobs always land in `new_enquiry` (preliminary screening is information only, never sets stage); repeat syncs never change stage; `source=qa_test` jobs are hidden from the admin pipeline by default. Why: no shared secret to leak; website result is preliminary.
- Mitti bridge: pure label-based prefill/parse in `mitti.core.ts`, the only network boundary in `mitti.server.ts` (`MITTI_API_TOKEN`, read per call). Sync reads only stored audit IDs, checks the template and Portal Job Number (blocks on mismatch), splits electrical fields → `assessments` and measure-up fields → `planMeasurementUpdate`; never status, PIESA records, stages or quotes. Measure-up-only template comes from `workflow_settings.mitti_measureup_template_id` (never invented). Non-standard or unrated work becomes `is_other` rectification items keyed by `external_key` and flagged `needs_office_pricing`; `completeAssessment` blocks until those items are priced. Why: `completeAssessment` stays the only completion gate, and Lovable never makes up a price.
- Site stage = two requirements: ceiling measure-up in `ceiling_measurements` (one `is_current` row drives quoting) and electrical/PIESA in `assessments`; visit scope derived only by `deriveScope` (`scope.core.ts`) via `jobScope`/`getJobScope`; `advanceSiteRequirements` is the only path to assessment_complete. Why: different people may do each part, and quotes must use the accepted measurement.
- Partner enquiries (property manager / installer partner / electrician-REC) live only in admin-only `partner_enquiries`, fed by signed `/api/public/partner-enquiry` (same Ed25519 key, pure `handlePartnerEnquiry` in `partner.core.ts`); never create jobs; Base44 status stored as `source_status`, admin owns `status`/`internal_notes`. Why: partner onboarding is not customer work and must not pollute the Pipeline.
- Activity 48 signing: quote acceptance signs `customer_agreements` (commercial, unlocks invoice/deposit) AND a separate binding conditional VEEC assignment in `customer_assignments` (`signed_stage='quote_stage_conditional'`, status `consumer_signed_pending_install`, needs approved `consumer_declaration`); never effective until install + AP QA fill `final_facts` on the same row and installer → AP sign; consumer re-signs only if template `requires_final_consumer_signature`, the form version changed, or a material variation. Non-payment never reverts it. `owner_esc_consents` stays separate (post-booking, ≥24h); `installer_declarations` post-install; `ready_for_veec` needs `effective_complete`. Why: HI VIC secures VEEC rights at quote without claiming effectiveness before the activity.
- Auto-progression uses only `autoAdvanceJob` over `planStep`/`runAutoAdvance`, calling `transition()`/`stageEntryBlockers()` and never Xero/Mitti or ambiguous decisions. Board lanes use `PIPELINE_PHASES`/`phaseForStage`; the lifecycle-first portal shows blockers and next actions before settings. Why: one safe automatic path and one visible source of truth.
- Gate 1: ONE pure categoriser `evaluateGate1` (`eligibility.core.ts`, ruleset `GATE1_RULESET_VERSION`) with locked order hard-fail -> internal REVIEW REQUIRED (`jobs.eligibility_review_required`, outcome null) -> needs_onsite -> likely; life support/roof/area/2026 rollout hold are `jobs.eligibility_flags`, never eligibility; applied only by `autoDecideEligibility` (re-evaluates system decisions idempotently by signature, never admin); progression via `eligibilityConfirmedFor`; Property Intelligence `recommendGate1` is an adapter over the same engine. Why: no contradictory parallel decisions; every result explainable.
- Property Intelligence (Gate 1 evidence) never writes Gate 1 itself; after each run it calls `autoDecideEligibility`, which accepts only trusted facts via `trustedIntel`/`applyIntelligence` (`eligibility.core.ts`: current, not stale, direct, high/very_high, public_gis/partner/provider; zoning/inferred facts may only raise review). Otherwise: pure rules in `intelligence.core.ts` (ruleset `RULESET`, `recommendGate1`, area hierarchy `canReplace`/`selectCurrentEstimate`, `ageStatusFor`), network only in `intelligence.gather.ts` (injected `FetchJson`, Vicmap open-data WFS `opendata.maps.vic.gov.au/geoserver/wfs` because the `vicmap.land.vic.gov.au` MapServers expose Map capability only), persistence in `intelligence.server.ts` (`property_intelligence_runs`/`property_facts`/`property_area_estimates`/`property_source_checks`). It never writes jobs.stage, eligibility fields or `properties.is_residential/year_built/enrichment`, never uses parcel area, never fabricates floor plans (provider slot `configuredProvider()` returns null). Why: remote evidence cannot legally prove Activity 48 eligibility; sources must be auditable.
- ESC pre-install controls: pure `esc.core.ts` (`readyToInstall`, `bookingLeadBlocker`, `buildEscPayload`, `staleReasons`, `submissionPatch`), persistence `esc.server.ts`; entry to `evidence_outstanding` is blocked unless READY TO INSTALL (Reg 23A consent, ESC notice sent, PIESA copies to owner + installer all ≥24h before start, PIESA window); installation bookings <24h ahead are rejected; `sent` only via adapter (none configured) or audited manual record with reference (DB check constraint). Extra notice fields come only from admin-approved `esc_notification_config`. Why: fail closed; never claim ESC was notified.
- PRE-LAUNCH comms lock: `workflow_settings.customer_comms_enabled` (default false, fails closed) checked by `assertCustomerCommsEnabled`/`customerCommsEnabled` in `comms.server.ts`; every outbound email/SMS/notification/customer request must call it (sendMessage email/sms, legacy requestOwnerAuthority). Portal/internal records stay allowed; autoAdvance graph is regression-tested free of delivery, Xero and Mitti calls. Why: QA must never message real customers or trades.

- Job File = read-only aggregation over existing records: pure `jobfile.core.ts` (`buildDocumentIndex` auto-files by source/kind, `visibleTo` role filter, `buildCorrespondence`, `buildTimeline`, `packSelection`/`planPack`/`buildManifest`), loading + ZIP export (fflate, server-side, stored under `<job>/exports/`, signed link only; >150MB → manifest + 7-day signed links) in `jobfile.server.ts`, server fns in `jobfile.functions.ts`. All communications (manual logs now, future email/SMS adapters) go to immutable `job_communications` via `recordCommunication`. Why: one source of truth per job, files indexed in place, role filtering server-side.
- Licensed providers (Pricefinder, Google Solar, Nearmap; Vicmap Buildings slot): parsers `providers.core.ts`, adapters `providers.gather.ts`, env-gated; Solar/Pricefinder area/age are supporting/`inferred` only (Solar = tier E footprint, BASE + one MEDIUM retry, roof risk operational). Why: only direct licensed evidence can feed Gate 1.
- Partner pilot: rules pure in `pilot.core.ts`, writes `pilot.functions.ts`/`pilot.server.ts`; approved + unexpired credentials gate partner work; imports stay draft until user confirms; offers never change channel/relationship owner; all bookings via `booking.server.ts` `confirmBooking`; split invoicing rejected. Why: attribution, no silent data, one booking gate.
- Installer-supplied measurements: imports create `ceiling_measurements` with `provenance='installer_supplied_provisional'`, supplied figures in immutable `supplied_*` columns, relevant area left empty (flagged) for an independent onsite trade; pure rules in `measurement.core.ts` (`acceptanceBlockers`, `verifierBlocker`, `measurementVariance`); admin accept blocked until `workflow_settings.measurement_standard_approved` + approved `partner_measurement_methods` row, aerial/remote never accepted; variance tolerance is admin config only (null = no judgement); config changes audited in `admin_config_events`. Why: pilot calibrates partner trust before measurements skip onsite verification.
- Assessment visits are scheduled only via `appointment_proposals` (AppointmentPanel → `respondToProposal` → `confirmBooking`); direct assessment `createBooking` is admin override only (`directBookingBlocker`, reason required, `admin_booking_override` event). Early owner "can't agree" goes to `requestReassignment` (review only, never unassigns); automatic electrician release only via `requestAnotherElectrician` after 48h/cannot-attend. Why: one booking path that the 24/48h rules can't be bypassed around.
- Base44 intake completion: pure rules in `enquiry.core.ts` (`buildBase44Raw`, `planContactConsent`, `planMediaImport`), persistence in `intake.server.ts`; consent goes to immutable `owner_contact_consents` (missing = unknown, no external contact; owner-targeted external delivery needs `assertCustomerDeliveryAllowed` = global lock then latest granted consent, stored copies use `customerDeliveryState`), media (25 MB/file, 40 MB total, matching Base44) copied once into private `job-files` as `documents` keyed by (job, `source_system='base44'`, `external_id`); media failures are logged for retry and never fail the enquiry; both run before Gate 1/intelligence. Why: Lovable keeps everything the owner already gave, without re-entry.
- Post-intake is a durable queue: `upsertEnquiry` stores Step 1 then `enqueueInitialGate1` (one `post_intake_work` row per job, `facts_version` from `eligibilityFactsKey` — address + Gate 1 answers only); `processPostIntakeWork` (`postintake.server.ts`, SKIP LOCKED claim `claim_post_intake_work`, leases, backoff, stale-run recovery) runs initial intelligence then the first official `autoDecideEligibility(..., { initialProcessor: true })`; other callers skip Gate 1 while work is active. Triggered best-effort via `ctx.waitUntil` (`background.server.ts`, wired in `server.ts`) and durably by pg_cron job `hivic-post-intake-worker` (every 2 min) calling `post_intake_tick()`, which mints a single-use nonce (`cron_nonces`, consumed by `consume_cron_nonce`) for `/api/public/hooks/post-intake` (also accepts the Bearer cron secret). Why: the webhook must ack fast; aborted requests left runs stuck and recorded evidence-poor decisions.

- Ready Check: $99 first step, credited once; then approved EEC/CII installer contacts owner and booking stores assignment, business and time. Never Xero/deposit/PIESA. Why: installer-led scheduling without an electrician/office bottleneck.
## LOCKED — STEP 2: AUTOMATIC GATE 1 CATEGORISATION
Status: COMPLETE, PRODUCTION-TESTED END-TO-END, LOCKED. Do not redesign or alter unless Jo explicitly asks.

Locked rules:
- Locked Step 1 Base44 intake is stored first and is the source of owner declarations, consent, media and preliminary screening.
- New enquiries enqueue durable initial_gate1 work in post_intake_work; Base44 must not wait for Property Intelligence/Gate 1.
- Immediate processing is best-effort; durable fallback cron hivic-post-intake-worker runs every 2 minutes.
- Worker uses protected auth, recovers stale leases/abandoned intelligence runs, runs Property Intelligence, then records exactly one official first Gate 1 system decision.
- Repeat/idempotent syncs do not duplicate jobs, consent, media, work or decisions when facts are unchanged.
- Step 2 uses the shared Step 1 mapping for answer fields.
- Customer outcomes: likely_eligible / needs_onsite_confirmation / does_not_appear_eligible.
- REVIEW REQUIRED is internal only.
- Hierarchy: hard failure → REVIEW REQUIRED → needs onsite → likely eligible.
- Owner-declared house/townhouse + verified Victorian premises + no trusted contrary class evidence may preliminarily pass residential, basis remains declared.
- Owner-declared relevant area >5 years + no contrary recent-construction/extension/storey evidence may preliminarily pass age, basis remains declared.
- Apartment/unit with unclear top-floor/relevant-ceiling status → REVIEW REQUIRED.
- Generic previous upgrade yes/unknown → REVIEW REQUIRED; only confirmed previous Activity 48 hard-fails.
- Insulation none declared → preliminary pass; present/unknown → Needs Onsite Confirmation; verified disqualifying insulation → hard fail.
- Life support is a safety flag only.
- Flat/low-slope/difficult access is an operational/onsite flag, not automatic ineligibility.
- Unknown area never fails; measure-required flag.
- Before 1 Oct 2026 private/general jobs are categorised normally but blocked from assessment dispatch by rollout_hold; the date condition clears from 1 Oct.
- Admin decisions are never overwritten.
- Every decision stores rule/fact/source/basis/result/reason/next action.
- Pipeline shows Likely eligible, Needs onsite confirmation, REVIEW REQUIRED; hard fail uses reversible On Hold.
- Base44 preliminary result is information only.
- No customer/trade communication is generated by Gate 1.
- Production proof: fresh live Base44 enquiry flowed through Step 1 → durable queue → Property Intelligence → one official Step 2 decision; 2-minute worker returned HTTP 200 and recovered abandoned QA intelligence runs.
- Customer email delivery config lives only in service-role `customer_delivery_settings` (id=1; enabled + https endpoint + >=32-char HMAC secret), read per call by async `configuredDeliveryAdapter`; it is a second lock after `customer_comms_enabled`. Post-intake email attempts (`attemptCustomerEmail`) are best-effort and never fail work; the 10-min `hivic-customer-followups` worker runs `processPendingInitialEstimateEmails` then `processDueFollowups`. Why: no secrets in env/source, two independent kill switches.
- Customer email safety: initial outcomes use only completed system/admin Gate 1 decisions; pending/review/unrecorded states hold. All sends retain unsubscribe, suppression, cutoff and `delivered_unrecorded` no-retry controls. Why: preliminary website results never trigger delivery, backlogs, or duplicates.
- Intake area invariant: `enquirySchema` requires `estimated_area_m2` (finite, >0, ≤5000); `area_unknown` only accepts false; `upsertEnquiry` always writes `estimated_area_unknown=false`; installer import confirmation also requires an area. Why: every new job must carry a preliminary ceiling estimate — no "I don't know" path.
- Calculator what-if address: type-ahead only via `VictorianAddressAutocomplete` → `address-search.functions.ts` read-only proxy to the website’s Base44 `address-search` service (no Lovable-held key); only a selected VIC detail (`acceptSelectedAddress`) feeds `resolveWhatIfLocation`/official v25 lookup; editing clears it; local state only, never persisted. Why: one address provider shared with the website, no unverified typed postcodes.
- Activity 48 AP compliance timeline is built only by pure `buildComplianceTimeline` (`compliance-timeline.core.ts`), reusing esc.core timing constants; auto-send switches `workflow_settings.auto_send_*` default off. Why: one auditable list of timed gates, manual-first launch.
- Activity 48 office records (life support plan, assignment copy, installer safety assessment, pre-install/completion owner docs, $200 co-payment) live in permanent `job_compliance_records` (immutable trigger); which stage each blocks is decided only by pure `complianceRecordBlockers` (`compliance-timeline.core.ts`), called from `stageEntryBlockers`. Why: timeline and enforcement share one rule list.
- REC and installer onboarding + signing live in the portal; signed applications are immutable, certificates private, and bank details stay private. Approval creates business-linked nominated workers; each trade user gets an individual profile matched by approved email and their business admin controls membership. Agreement wording changes require a new version. Why: one review queue, no shared logins or repeated onboarding.
