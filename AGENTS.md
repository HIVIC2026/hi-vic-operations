## Architecture rules
- All writes go through `src/lib/portal.functions.ts` (caller role check) → central `workflow.server.ts` / `quotes.server.ts` / `xero.server.ts` using the service role; non-admins have no RLS write policies. Why: one place for workflow, pricing and payment gates.
- Stage-entry guards (Owner Authority, PIESA window, 50% deposit, evidence, compliance) live only in `stageEntryBlockers`; authority rules live in `authority.server.ts`. Why: rules change centrally.
- One combined installation quote (rectification lines folded in) carries the single Xero invoice and 50% deposit. Why: deposit must precede rectification scheduling.
- PIESA window length lives in `workflow_settings`; deadline/urgency computed by the `job_piesa_deadlines` view. Why: single source for UI and server.
- Payment display state is derived by the `invoice_status` view (customer-safe columns; internal Xero IDs admin-only via server fn); Xero is the system of record. Why: time-based states need no cron.
- Internal pricing (cost/margin/fee) lives only in admin-only `quote_internals`; customer-facing prices in `quote_items` are inc GST. Why: never expose margins.
- Evidence files live in the private `job-files` bucket, accessed only via server-issued signed URLs. Why: no public evidence URLs.
- See `docs/PORTAL.md` for workflow and the security test matrix.
- Write every server function as a literal `createServerFn(...).middleware(...).inputValidator(...).handler(...)` chain; never wrap `createServerFn` in a helper factory. Why: the compiler only turns literal chains into server calls — a factory made handlers run in the browser.
- Never import `@tanstack/react-start/server` in `*.functions.ts` or modules they import; read request data via a `createMiddleware().server()` (see `request-meta.ts`). Why: that import is denied in the browser bundle and crashes every page.
- Job source lives in `jobs.channel` (+ originating installer business/user), made permanent by the `guard_job_source` trigger; installer-sourced jobs get one quote from the assigned installer and stay payment-gated via `commercialBlocker` until `commercial_model = hivic_invoices_owner`. Why: attribution is audit evidence; installer invoicing isn't defined yet.
- ONE full detailed Xero invoice per accepted quote (unique quote_id, reference `HI VIC <job>`, all quote lines + negative VEEC line, Inclusive GST, Business Unit = Home Insulation Victoria (legacy Projects never used)); 50% deposit via Xero native Request Deposit raised manually (admin records `deposit_request_raised_*`, never unlocks); gate opens only when Xero cumulative AmountPaid ≥ 50% or audited override; install date = same invoice due date (`balance_due_date`, update flagged `xero_update_pending`, sent only if `XERO_DUE_DATE_UPDATES_ENABLED`); pure logic in `invoice.lifecycle.ts`/`xero.core.ts`, mocked tests `bun test ./tests/`. Why: Xero API cannot create native deposit requests; one invoice keeps totals and audit simple.
- Xero business-unit barrier: `jobs.business_unit` (immutable via `guard_job_source` trigger, set explicitly to 'hivic' in `upsertEnquiry`) must equal 'hivic' before every Xero step — `requireHivicInvoice`/`requireHivicJob` in `xero.server.ts` plus `assertHivicPayload`/`assertHivicReference` in `xero.core.ts`; fail closed. Why: the connected DC Construction Solutions Xero org must never be automated for non-HI VIC work.
- Base44 enquiry webhook is verified by Ed25519 (public key in `enquiry.core.ts`, header `x-hivic-signature`, optional `x-hivic-key-id: base44-v1`) before parsing; preliminary result (`preliminary_outcome`/`preliminary_reasons`, planned by pure `planBase44Job`) and `life_support_status` are accepted only from source `base44`; new website jobs always land in `new_enquiry` (preliminary screening is information only, never sets stage); repeat syncs never change stage; `source=qa_test` jobs are hidden from the admin pipeline by default. Why: no shared secret to leak; website result is preliminary.
- Mitti bridge: pure label-based prefill/parse in `mitti.core.ts`, the only network boundary in `mitti.server.ts` (`MITTI_API_TOKEN`, read per call). Sync reads only stored audit IDs, checks the template and Portal Job Number (blocks on mismatch), splits electrical fields → `assessments` and measure-up fields → `planMeasurementUpdate`; never status, PIESA records, stages or quotes. Measure-up-only template comes from `workflow_settings.mitti_measureup_template_id` (never invented). Non-standard or unrated work becomes `is_other` rectification items keyed by `external_key` and flagged `needs_office_pricing`; `completeAssessment` blocks until those items are priced. Why: `completeAssessment` stays the only completion gate, and Lovable never makes up a price.
- Site stage = two requirements: ceiling measure-up in `ceiling_measurements` (one `is_current` row drives quoting) and electrical/PIESA in `assessments`; visit scope derived only by `deriveScope` (`scope.core.ts`) via `jobScope`/`getJobScope`; `advanceSiteRequirements` is the only path to assessment_complete. Why: different people may do each part, and quotes must use the accepted measurement.
- Partner enquiries (property manager / installer partner / electrician-REC) live only in admin-only `partner_enquiries`, fed by signed `/api/public/partner-enquiry` (same Ed25519 key, pure `handlePartnerEnquiry` in `partner.core.ts`); never create jobs; Base44 status stored as `source_status`, admin owns `status`/`internal_notes`. Why: partner onboarding is not customer work and must not pollute the Pipeline.
- Customer Acceptance & VEEC Assignment (`customer_assignments`, rules only in `assignment.core.ts` `evaluateAssignment`, writes in `assignment.server.ts`) is signed at installation-quote acceptance; effective only after install + installer declaration + final product/m²; official wording only from admin-approved versioned `compliance_templates` (signing blocked until configured). `owner_authorities` is deprecated history, no longer a gate. Templates = static `body` wording + structured `form_fields` (parsed by `parseFormFields`) that electronic forms render; known facts are prefilled (`prefillRows`, `resolveInstalledDetails`), never retyped; optional AP declaration is an internal admin e-sign (`signApDeclaration`) required only when an approved required `ap_declaration` is active; not-ready messages come from `NOT_READY` and customers never see a broken form. `/admin/compliance` is admin configuration only. Why: assignment cannot precede the prescribed activity, wording must never be invented, and nobody fills in paper forms.
- Auto-progression lives only in `autoAdvanceJob` (`autoadvance.server.ts`) over the pure planner `planStep`/`runAutoAdvance` (`autoadvance.core.ts`); it only uses `transition()`/`stageEntryBlockers()`, never calls Xero/Mitti, and never automates ambiguous eligibility (see Gate 1 auto-decision rule), contractor choice, quote acceptance, measure-up approval, AP judgement, overrides or VEEC data (ap_review → ready_for_veec only with `allowApPromotion` from admin compliance actions). Board lanes come from `PIPELINE_PHASES`/`phaseForStage` in `workflow.ts`. Why: one safe place for automatic moves; detailed stages stay the source of truth.
- Gate 1 auto-decision: facts resolved by pure `resolveGate1Facts` then `evaluateGate1` (`eligibility.core.ts`, per-rule evidence with source + basis verified/recorded/declared/unknown), applied only by `autoDecideEligibility` (`eligibility.server.ts`; `previewGate1` is read-only for the admin panel). Base44 evidence is stored by pure `buildBase44Evidence` under `properties.enrichment.base44` (`declared` vs `research`; `age_verified` only for complete research with a first-appearance year). Portal columns beat Base44; declarations never become verified; only `DECLARATION_ALLOWED` rules pass on a declaration; hard auto-fail only on recorded/verified objective facts (non-VIC, non-residential column, verified too-new year) and holds `on_hold`; conflicts/unknowns -> review. Never overrides `source='admin'`. Why: clear cases flow, declarations stay auditable.
- Property Intelligence (Gate 1 evidence) never writes Gate 1 itself; after each run it calls `autoDecideEligibility`, which accepts only trusted facts via `trustedIntel`/`applyIntelligence` (`eligibility.core.ts`: current, not stale, direct, high/very_high, public_gis/partner/provider; zoning/inferred facts may only raise review). Otherwise: pure rules in `intelligence.core.ts` (ruleset `RULESET`, `recommendGate1`, area hierarchy `canReplace`/`selectCurrentEstimate`, `ageStatusFor`), network only in `intelligence.gather.ts` (injected `FetchJson`, Vicmap open-data WFS `opendata.maps.vic.gov.au/geoserver/wfs` because the `vicmap.land.vic.gov.au` MapServers expose Map capability only), persistence in `intelligence.server.ts` (`property_intelligence_runs`/`property_facts`/`property_area_estimates`/`property_source_checks`). It never writes jobs.stage, eligibility fields or `properties.is_residential/year_built/enrichment`, never uses parcel area, never fabricates floor plans (provider slot `configuredProvider()` returns null). Why: remote evidence cannot legally prove Activity 48 eligibility; sources must be auditable.
- ESC pre-install controls: pure `esc.core.ts` (`readyToInstall`, `bookingLeadBlocker`, `buildEscPayload`, `staleReasons`, `submissionPatch`), persistence `esc.server.ts`; entry to `evidence_outstanding` is blocked unless READY TO INSTALL (Reg 23A consent, ESC notice sent, PIESA copies to owner + installer all ≥24h before start, PIESA window); installation bookings <24h ahead are rejected; `sent` only via adapter (none configured) or audited manual record with reference (DB check constraint). Extra notice fields come only from admin-approved `esc_notification_config`. Why: fail closed; never claim ESC was notified.
- PRE-LAUNCH comms lock: `workflow_settings.customer_comms_enabled` (default false, fails closed) checked by `assertCustomerCommsEnabled`/`customerCommsEnabled` in `comms.server.ts`; every outbound email/SMS/notification/customer request must call it (sendMessage email/sms, legacy requestOwnerAuthority). Portal/internal records stay allowed; autoAdvance graph is regression-tested free of delivery, Xero and Mitti calls. Why: QA must never message real customers or trades.

- Job File = read-only aggregation over existing records: pure `jobfile.core.ts` (`buildDocumentIndex` auto-files by source/kind, `visibleTo` role filter, `buildCorrespondence`, `buildTimeline`, `packSelection`/`planPack`/`buildManifest`), loading + ZIP export (fflate, server-side, stored under `<job>/exports/`, signed link only; >150MB → manifest + 7-day signed links) in `jobfile.server.ts`, server fns in `jobfile.functions.ts`. All communications (manual logs now, future email/SMS adapters) go to immutable `job_communications` via `recordCommunication`. Why: one source of truth per job, files indexed in place, role filtering server-side.
