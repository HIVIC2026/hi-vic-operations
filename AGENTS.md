# Project rules
- Held visit messages use the fail-closed shared lookup before records/sends; suppress approved templates and adapt authorized scheduling displays, never domain writers. Why: no legacy time negotiation alongside partner booking.
- In-house visit booking uses the existing held lookup and active business membership before confirmBooking; that member-checked reader also supplies current booking rows. Legacy scheduling remains until access is positively allowed; booked install readouts stay read-only for in-house partners. Only partner-billed in-house rectification skips its HIV payment check, all other guards and writers stay unchanged. Why: partner scheduling must not bypass payment, PIESA, consent, Part C or ESC controls or hide recorded visits.
- In-house suppression reads every active installer/business assignment regardless of job source/deletion; candidate exclusions stay in sweeps. Joined reads page to exhaustion in 200-row pages and 200-id scopes; any failure logs and discards partial results. Skipped actions return ok:false and callers show the message before success. Partner-call notices and booking/payment guards never use suppression. Why: TEST parity, row caps and failed reads must not dispatch or falsely report success.
- In-house batches use admin-bound server functions and a service-only per-job locked RPC with coverage validation; allocation records pending email intent, never ledger rows. Approved notices use the existing guarded sender immediately or via the periodic tick, with one per-job key. Why: atomic allocation must not duplicate assignments, weaken payment gates or deliver unapproved messages.
- In-house partner configuration uses a pure in-house core, business-owned active effective PIESA rate-card lines, admin-checked saveBusiness and an atomic configuration/history RPC; job-less change/backfill history goes to admin_config_events because workflow_events requires a job. Batched reads propagate errors on money paths, missing rates hold quotes, and only trade display catches read failures. Why: preserve accepted configuration and audit history without violating the job constraint or allowing fallback pricing.
- First-response unknown-age qualification uses `firstResponseOutcome` against the current recorded audit without rewriting Gate 1; routing, campaign links and rendering share it. Why: no-insulation age-unknown owners must not fall between offer paths, while failed or missing gates stay blocked.
- Journey run path/group/status metadata is optional and stored by the existing storeJourneyRun helper; Drizzle SQL migrations own schema changes and drizzle/schema.ts stays the generated placeholder. Why: legacy callers/rows remain compatible and migration metadata has one owner.
- Declared coverage proposals live in a pure centroid-based core and are office-only suggestions saved through existing saveBusiness verification; matching never reads proposals. Why: partner declarations must not become verified coverage without office confirmation.
- One-job TEST timing sweeps validate qa_test and suppress senders; browser runs persist a per-job no-delivery marker checked at delivery boundaries. Why: QA must not sweep other jobs or send from the running server.
- Simulated Ready Check browser completion requires active installer assignment, reserved TEST identity, active qa_test job and exact simulated measurement pointer; it uses the normal Mitti read afterwards. Why: TEST completion must not open real forms or bypass workflow guards.
- Historical Ready Check day links return to the job page after that visit is no longer current. Why: old bookings must not appear to be today's installation work.
- Mitti identity reuse binds every active job-number field and worker/profile/history email; ambiguous user IDs fail closed. Why: duplicate fields or stale person links must never hand a form to the wrong identity.
- Fixes gates read the newest non-superseded quote; generation uses content-based stable quote/line keys and checked writes. A5 completion requires job/audit-bound summaries and successful file copies. Why: stale approvals and interrupted persistence must never unlock work or duplicate records.
- TEST office is a separate deny-by-default capability, never an admin alias: exact route/function allowlists, verified identity, persisted roles, scoped job/business graph checks and database API/RLS/storage boundaries protect its permitted journey surfaces; all other capabilities remain refused. Why: privileged office readers bypass RLS and new screens must never implicitly expose real records.
- Completed Ready Check edits use the validated same-audit refresh helper before held-only redrafting; Add a job runs the existing claim-guarded form creator immediately without delayed retries. Why: completed facts must not go stale and absent request lifecycle must not postpone first creation to the tick.
- Existing-form Mitti pulls and completed Ready Check retries live in the dedicated authenticated Mitti pull callback, separate from allocation; activate its production schedule together with that deployment. Why: slow allocation must not starve form reads or leave a deployment gap.
- Campaign spot saves use one database transaction for response, save event and queue stage; secure next visits repair only recorded saves, without delivery. Why: interrupted requests and replays must not strand saved spots or send repair messages.
- Verified post-Ready-Check ineligible notifications share the existing T7 per-job email key and guarded sender; only durable held records retry after revalidating the current final verification. Why: no duplicate messages, no Gate 1 mutation or historical backlog release.
- Document early recovery owns module error/rejection events; the router handles preload/route catches and cache-busts reloads; both use the pure page-recovery stale-export classifier. Why: competing refresh handlers or missed named lazy exports can leave stale tabs blank.
- Read nested `AGENTS.md`, including `src/lib` and `scripts`, before edits. Why: scoped safeguards.
- Server functions are literal `createServerFn(...).middleware(...).inputValidator(...).handler(...)` chains; never import `@tanstack/react-start/server` in `*.functions.ts`. Why: factories/that import break the client bundle.
- Test Centre: `source='qa_test'`, bypass post-intake. Why: no live automation.
- Journey TEST-trade setup snapshots and restores both offer-preference flags alongside coverage. Why: temporary practice readiness must not undo office-paused dummy trades.
- `/` on every customer host and `/calculator` serve the same current public calculator; staff sign in at `/auth`, and on the staff host (`staff-host.core.ts`, portal.homeinsulationvictoria.com.au, decision 381) `/` opens `/auth`. Secure estimates never embed the retired what-if calculator or track calculator use. Why: preserve customer links and one calculator without obsolete variants.
- The server entry detaches GET/HEAD rendering requests from the local adapter's socket-owned abort signal; keep mutation requests unchanged. Why: cancelled preview navigation must not throw after response close and blank the page.
- Portal look lives in `src/styles.css` tokens (`.portal-theme`) plus pure presentation pieces in `src/components/portal/kit.tsx`; redesign phases use these presentation pieces; phase 3 may add canonical office navigation/routes and compact actual job pages but never change domain guards or workflow. Why: agreed office simplification preserves operational behaviour.

- Portal QA: `bun run portal-qa` only; gaps NOT_RUN, never PASS. Why: honest checks.
- `journey --screens` is browser-first evidence with a fail-closed preflight, never the legacy server-driven setup; unproven website sandbox, server-wide provider guards, TEST-domain actors or rule mismatches block downstream actions. Why: command-process guards cannot protect browser-triggered server mutations, and screenshots after direct server actions are not screen proof.
- Screen walk-through starts from the journey s1 qa_test job (website form is portal-qa's), probes message/Mitti/Demo safeguards for that job before any page action, and marks unreached steps BLOCKED/NOT RUN. Why: honest page evidence without manufacturing downstream state.
- Screen journey selects the isolated Bravo persona with people preparation disabled; records release before owner confirmation, attempts independent pages after failures, and restores only selected TEST businesses. Why: Alpha's historical non-qa_test link must remain untouched and QA must not approve people to bypass gates.
- `realMittiCall` routes TEST people (reserved domain, TEST_MITTI_ASSIGNEE), sim_ ids and stored `mitti_sim_audits` ids to the persistent simulator; `mittiCallFor` swaps whole TEST flows including template reads. Why: browser-driven TEST jobs in the running portal never reach real Mitti, real calls stay byte-identical.
- QA scripts resolve server-function IDs from the target's served dev transform or served compiled client (`scripts/qa-serverfn-resolve.ts`); unresolved = diagnostic failure, never a permission result. Office bulk lookups by job id are batched. Why: guessed IDs gave 500s and one all-ids URL stalled Office reads for minutes.

- Read `src/AGENTS.md` before source edits or scripts exercising app flows, then narrower guidance. Why: preserve domain safeguards without duplicating them here.
- RLS policies call per-user helpers as sub-selects (`(SELECT is_admin())`, `(SELECT auth.uid())`, `(SELECT has_role((SELECT auth.uid()), ...))`); new policies follow the same form (applied 26 Oct 2026, `docs/pending-migrations/rls-initplan-speed.sql`). Why: evaluated once per query instead of once per row, same rows.
- Clear owner decline emails auto-close only unbooked, unpaid enquiry jobs through `cancelJobFully` (`email-decline-close.server.ts`, gate `declineAutoClose`), with no reply; anything else keeps the Apply card. Why: booked/paid cancels release trades and need the office.
- Repeat PIESA after a lapsed 30-day window: pure `src/lib/repeat-piesa.core.ts` + `repeat-piesa.server.ts`; office chooses payer (append-only `repeat_piesa_*` workflow events per deadline), `repeatPiesaPayer` is a suggestion only; price setting is append-only `admin_config_events` `repeat_piesa_price_set`; gate joins `piesaRequestBlockers`; owner-pays makes its OWN Xero invoice (kind `repeat_safety_check`, reference `… safety check 2`, 3, 4…; batch 3b), paid only once that invoice is paid in full (`repeatInvoicePaid`). A reopen at or after the PIESA stage (`reopenStageFor`) supersedes the old check and reuses this flow keyed `reopen:<iso>`: the owner pays again only if a check was done since the last reopen, and an already-paid repeat not yet done carries over unless refunded (`reopenRepeatDecision`). Why: nothing decides or charges a repeat check without the office.
- Repeat PIESA payment step (Jo 29 Oct): counts only its own invoice — the repeat invoice paid in full, nothing else; it is never counted toward the deposit/balance; it sits straight after the first safety check; a Stripe card payment on the repeat invoice records it paid at once (`repeatPaidByCard`); the owner's repeat card disappears at stage `offer`. Why: the repeat check showed owing after payment and the owner page stuck on the card.
- Stripe keys: TEST jobs read only `STRIPE_TEST_SECRET_KEY` (sk_test_), real jobs only `STRIPE_SECRET_KEY` (`stripeKeyFor`). Why: test card runs can never touch the live key.
- `workflow_settings.sms_message_switches` is guarded by DB trigger `trg_guard_sms_message_switches`: every change writes an `sms_switches_db_change` audit row and bumps updated_at; changing >1 switch in one write is refused unless the transaction sets `hivic.bulk_switch_change=approved`. Why: an unaudited out-of-band write turned every switch off on 29 Oct.
