# Office performance — 25 Oct 2026

Jo: "Needs me is INCREDIBLY slow, the whole portal is, it's not usable."

Live facts (pg_stat_statements since 28 Sep; 2,186 jobs, 40k workflow_events, 31 MB; the database itself was not
saturated — 1 active query when sampled). The slowness is **round trips and over-reading from the worker**, plus a few
**missing indexes** that turn views into per-job sequential scans.

## How this was measured

No guessing and no live database: `tests/helpers/query-counter-db.ts` is an in-memory PostgREST stand-in that counts
every request, the rows returned, and the sequential **waves** (idle→busy transitions = round trips the user waits
for). Latency is an explicit model (fixed time per request), so `PERF_RTT=50` (50 ms per trip, a realistic
worker→Supabase round trip under load) turns a waterfall into wall time. The synthetic office is 2,200 jobs, a quarter
live, with realistic child rows (stage history, sends, bookings, quotes, one draft quote per ten live jobs…).

```
PERF_REPORT=1 PERF_RTT=50 bun test tests/office-read-budget.test.ts     # Needs me, Jobs › Active, Enquiries
PERF_REPORT=1 PERF_TRACE=1 bun test tests/office-read-budget.test.ts     # + which file:line issued each request
PERF_REPORT=1 bun test tests/tick-sweep-budget.test.ts                   # read cost of every 15-minute tick sweep
```

Both tests keep budgets as regression guards (writes are refused, network is blocked).

## Needs me — what it did per load (before)

`admin.needs-me.tsx` → `getNeedsMePage` → `loadNeedsMePage` → `gatherNeedsFacts` → `loadOffice` + `loadQuotesToCheck`.

1. `loadOffice` read **every job** (2,186 incl. closed/deleted/TEST), then 24 **whole-table** reads with no job filter
   — including `workflow_events` `stage_changed` for all history (the live "select job_id,to_stage,created_at where
   event_type=…" — 5,892 calls, 152 ms mean, paged 1,000 at a time **sequentially**), every email/message ever sent,
   all bookings, quotes, invoices, and the `job_piesa_deadlines` view for every job (whose lateral PIESA lookup had no
   index → per-job seq scan of `piesa_records`).
2. Then ~12 more **sequential** round trips: office picks → offers after picks → timed offers → sends → Ready Check
   requests → Mitti sync errors → measure-ups → owner paperwork signatures → partner change requests → text failures →
   the settings row (read a second and third time) → pending workers → daily-text settings → trade-expiry reads.
3. Then `gatherNeedsFacts` started its own 17 reads **only after** `loadOffice` finished, then fixes drafts, then
   Quotes to check (twice with TEST on, one after the other), then ~8 more sequential follow-ups (returned offers, AP
   hold reasons, robot failures, PIISA alerts, deposits, compliance flags, email items, REC links, review feedback).
4. `loadQuotesToCheck` read candidate jobs in 50-id batches, 4 at a time, and the business names after, then the
   readiness guards 10 at a time; `officeQuoteBlockers` read the current measurement twice.
5. Client: `refetchInterval` 120 s, `staleTime` 30 s, React Query default 3 retries — a slow failure tripled the load,
   and every return to the tab after 30 s reloaded the whole page.

Also O(n²) loops in JS (`ids.includes`, `gsig.filter` per job, `jobs.find` per row).

## What changed

- **`loadOffice`** (`office.server.ts`): the job read is filtered in the database (deleted / QA-archived / TEST, and
  for Needs me `openOnly` — complete/cancelled are always status "ended", which Needs me dropped anyway). Every per-job
  read is scoped to the live job ids in **bounded 200-id chunks, all in flight together**. Two waves: (1) jobs +
  everything independent of them (settings row once, snoozes, applications, picks, Mitti errors, change requests,
  text failures, pending workers, daily-text settings, dispatch mode/hours, approved paperwork versions, trade-expiry
  reads); (2) every per-job read. `job_piesa_deadlines` is read for those ids only and only rows with a deadline.
  Maps instead of O(n²) scans. Same rules, same output.
- **`gatherNeedsFacts`** (`office-needs.server.ts`): three waves — (1) `loadOffice` and every Needs-me read that does
  not depend on it, Quotes to check (live + TEST in parallel), robot failures, email items, REC links, review
  feedback; (2) all follow-ups at once (returned offers, consent / AP hold reasons, PIISA forms, deposit views,
  compliance flags, email/feedback job names); (3) the pure rules, in the original order. `byIds` chunks run in
  parallel.
- **`loadQuotesToCheck`**: 150-id chunks all at once, business names read alongside, readiness guards in a pool of 20;
  `officeQuoteBlockers` reads the measurement once and runs the product check in the first wave.
- **Jobs › Active** (`office-lists.server.ts`): one `loadOffice` call for all live ids (was one sequential call per
  150 jobs); `byIds` 8 chunks in flight (was 4).
- **Needs me client**: `staleTime` 60 s, `retry: 1` (poll stays 120 s, paused in background tabs by React Query).
- **Tick** (`allocation-tick.ts`): `timingsMs` per sweep in the tick's JSON response, so the slow sweeps are visible in
  the cron log. Sweeps batched: PIESA owner confirmations and electrical-fixes confirmations decide every job's next
  step from one batched read (`duePiesaConfirmSteps` / `dueFixesConfirmSteps`, same `nextPiesaConfirmStep` rule; the
  send path re-reads everything itself); completion packs skip "already sent" / "not paid in full" from one batched
  read (`invoiceFullyPaid` now pure in `completion-pack.core.ts`); final invoices skip recorded O45 keys; provisional
  bookings skip started bookings already alerted and read payment views 5 at a time (actions stay one at a time).
  Helpers: `sweep-batch.core.ts` (pure) and `sweep-batch.server.ts` (batched reads, fail loudly).

|---|---|

| `workflow_events (job_id, event_type, created_at desc)` | the 3.8 M per-job event-type checks |
| `property_facts (property_id, fact_key) where is_current` | property_facts reads 632 ms mean (by property) |
| `external_sync_logs (created_at desc) where status='error'` | Needs me's "Mitti sync failed in 3 days" scanned the log on every load |

Proof: `tests/perf-2026-10-25-indexes-practice-db.test.ts` (applies twice; each index is chosen for its query with
seq scans disabled, including the deadline view's lateral; view results unchanged; rollback removes exactly these).

## Not changed — next candidates (with the reason)

- **`onsiteOnlyOfficeJobIds`** reads `office_enquiry_index` where `office_bucket = 'onsite_wait'` on every Needs me
  load. No SQL in this repo produces that bucket, so it probably always returns nothing — but it forces the whole
  enquiry view (≈650 ms DB time) to be computed. Check live: `select count(*) from office_enquiry_index where
  office_bucket='onsite_wait'`; if 0 and the view has no such bucket, the read can go.
- **`office_enquiry_index`** itself computes ~20 correlated subqueries + a window over every job for each read; the
  Enquiries list reads it in full on every search/sort/page. Index #3 removes the worst part; materialising the per-job
  facts would be the next step (a DB change — not attempted here).
- **Closed jobs list** (`job-list-page.server.ts`): page read with `count: 'exact'` + 4 exact head counts + a 5,000-row
  stage read over `office_job_list` per page view (6 evaluations of the view). Index #1 makes each much cheaper; the
  pile counts could come from one grouped read later.
- **Install day sweeps**: `sweepInstallDays`, `sweepInstallClearance` and `sweepInstallWindowRule` each build the same
  ~10-read `installDayContext` per `installation_scheduling` job, three times per tick (781 requests each on the
  synthetic office). One shared pass would cut two thirds; left because the three sweeps write between each other.
- `sweepElectricianAttendance` (≈7 reads per booking), `sweepPiesaCopyDeliveries` (≈6 per booking), `sweepPrestart`,
  `sweepDailyBrief` (once a day) — per-job reads remain; `timingsMs` will show whether they matter live.
- Legacy `office_enquiry_page` RPC (1,609 calls historical) is no longer called by any screen.
- Trade screens poll every 30–60 s per open phone (`/field`, `/field/day`); not office, not changed.
